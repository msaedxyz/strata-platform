## 1. What we built

### Write API (docs/api-contract.md)

| Module | Endpoints |
|---|---|
| services/api/routers/governance.py | GET /api/proposals?status=&kind=, GET /api/proposals/{id}, POST /api/proposals/{id}/approve, /reject, /edit-approve, POST /api/alerts/{id}/acknowledge, /confirm, /dismiss, GET /api/telemetry/alerts, GET /api/persons/{id}, POST /api/persons/{id}/erase |
| services/api/routers/engagement.py | POST /api/deals/{id}/stage, /contacts, /touchpoints, /next-action, /prequalification |
| services/api/routers/errors.py | Maps the domain errors: 403 own proposal, 404 unknown id, 409 already decided, 422 broken rule, 503 no master key |

1. Each endpoint has the role of the contract. The API enforces the role. A viewer gets 403 on each write endpoint.
2. The approval queue gives each proposal with its proposed events and its evidence items: the quote, the character offsets, the source URL, the title and the publisher. Each item also has `created_by_me`.
3. Approve and edit and approve give 403 to the creator of the proposal (docs/06 rule 2). Reject needs a reason (422 without). An `admin_review` proposal needs an admin. A SourceProposed proposal goes through `approve-source` only (409 on `approve`).
4. POST /api/deals/{id}/stage writes a DealStageChanged proposal (policy review) with the analyst as the creator. The ProposalCreated projection sets `proj_deal.stage_pending`, so the card shows the pending stage. A second move while one waits gives 409.
5. The engagement endpoints write ContactAdded, TouchpointLogged, NextActionSet and PrequalificationStatusChanged through `create_proposal` with the user as the creator (policy automatic, actor human). `create_proposal` now refuses an engagement event from an agent (the `actor: human` rule of config/approval-policy.yaml).
6. The alert endpoints write AlertAcknowledged (analyst), AlertConfirmed and AlertDismissed with `false_positive` (approver), as human events. A decision cites the evidence of the alert.
7. Audit log (docs/06): each user action that changes data is an event with actor type human. New event types: SourceAdded (manual upload), BriefVersionCreated (new brief version) and PersonErased.
8. The typed client in packages/api-client is regenerated.

Additions to the contract that do not break it: an optional `person_id` in the contact body, an optional `reason` in the stage move and in approve, a `kind` filter on the proposal list, GET /api/proposals/{id} and GET /api/persons/{id}.

### Tier 0 alerts and telemetry

1. `raise_alert()` writes AlertRaised at once with the status unconfirmed. It records a "broadcast" delivery row for the frontend channel. The live stream (/api/live) adds the alert and `alert_status` to each message of stream `alert`, and records a "delivered" row when it sends an AlertRaised message to a connected client. Email records the SMTP send time.
2. /api/ticker and /api/signals items carry `alert_id` and `alert_status` (a join on `proj_alert.signal_id` or `source_id`).
3. GET /api/telemetry/alerts gives for each alert: the published, fetched and raised timestamps, the delivery time for each channel, the acknowledgement time and user, the decision time and user, the outcome (confirmed, dismissed, false_positive) and the tier rule. Metrics: latency from fetch to alert (n, median, p90), time to acknowledgement (n, median, p90) and the false positive rate for each tier rule.

### Personal data (services/governance/personal.py, config/personal-data.yaml)

1. Each person has a random 256-bit data key. STRATA_MASTER_KEY wraps it with AES-256-GCM. The wrapped key is in `person_key`.
2. The name, business email and business phone are encrypted with the key of the person (AES-256-GCM, the entity id is the associated data). EntityIdentified of a person and ContactAdded hold the encrypted blob in `payload.personal` only. The event schema of ContactAdded refuses clear name, email and phone.
3. A blind index (HMAC-SHA256 of the business email, else of the name and the organisation) finds an existing person. It is in the key row, so the erasure deletes it too.
4. POST /api/persons/{id}/erase (admin) deletes the key row, writes an `erasure` record to `security_log` and a PersonErased event. After the erasure the API gives `name: "[erased]"`, `email: null`, `phone: null` and `erased: true`. `check_hash_chain()` still reports zero breaks.
5. GET /api/deals/{id}/relationship decrypts the contact fields. The response shape does not change.
6. Migration db/migrations/0300_governance.sql: `event_evidence_exempt()` lets a person entity that a user adds (EntityIdentified, actor human, type person, encrypted fields) pass the evidence constraint, as the team is the source (docs/03). `fact_evidence_problems()` uses the same exemption. The migration also adds `person_key.lookup_hash` and indexes.

From the known risks of reports/M3.md and the review of the snapshot run by the lead:

| The one-stop border keyword fired on delay stories | transport_infrastructure_project needs project words in the document (theme_requires_context) |

| Poor project names ("Peek Into The ...", "Solar Project") | Title boundary words, title separators and a distinctive word rule (config) |
| Duplicate projects at one site | A project mention that names the site of one known project of the same kind is that project |
| Title cues for stages | "Construction of X kicks off", "Announces Commissioning of", "Mine Restart" |
| "<project> is at a site" | The title names the site |

## 6. Known risks for M6

1. The frontend must show `alert_status` in the ticker, the signal feed and the alert panel. Live messages of stream `alert` carry `alert` and `alert_status`.
2. The priority list calculator does not exist yet (docs/05 scorer rules 5 and 6, scenario 17 rank part). `proj_deal.priority_score` stays null.
3. Held-out extraction precision and recall are below the targets (held-out 2: 0.818 and 0.643). The gold numbers are optimistic. The Anthropic backend has no numbers.
4. The Tier 0 rule "enters the engagement window" fires when the stage before is unknown. This can raise the alert volume. Check it with Mohamed.
5. Touchpoint notes are free text and are not encrypted. A note can hold personal data that erasure does not remove.
6. The master key has no rotation. A new STRATA_MASTER_KEY needs a re-wrap of each person key.
7. Two sites that share a first word and have no sole distinctive word still give no site link for a project name.
8. The backtest dataset has 7 events. docs/09 needs 20.
9. The criterion 06-4 test and scenario 1 start the API in a uvicorn thread on a local port. CI must allow it.
10. Merge risk with Track 2: packages/api-client (regenerated), tests/python/conftest.py (one new import line) and services/api/routers/read.py (ticker, signals and relationship changes). The contract additions in section 1 are optional fields and new read routes.
