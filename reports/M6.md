### 1.2 Priority list calculator (docs/05 scorer rules 5 and 6)

- services/projections/priority.py is a projector hook (projector.register_hook). It runs after the folds of each event, in the insert transaction and in a rebuild.
- It recalculates the deals that an event can change: deal and engagement events, project events (stage, forecast, demand estimate, identity, relationships, facts), relationship events that name the project, the site or the organisation of a deal, retractions, and a demand estimate of a site.
- It writes proj_deal.priority_score, priority_breakdown, lead_time_days, demand_litres_month, confidence and buyer_fit.
- Lead time: days from the "as of" date of the calculation to the forecast start of the project of the deal. The "as of" date is the recorded time of the event that caused the calculation, so a rebuild gives the same values.
- Demand: the approved DemandEstimated of the project, else of its site.
- Confidence: the certainty of the DealIdentified evidence.
- Buyer fit: the best buyer role of the project and the site. A mining, haulage or EPC contractor scores highest. An owner that buys fuel directly (the organisation of the deal, or the operator of the site when no contractor is known) scores higher than an owner.
- Rule 6: a deal whose project is in the engagement window and has no contact found gets a boost, and the list puts it first in its group.
- Each part of the breakdown has its value, score, weight, contribution, event ids and evidence ids.
- config/priority.yaml holds the weights, the score points, the certainty and role scores, the groups (deal stage bands), the rule and the opportunity rule.
- GET /api/priority orders by group, then the rule, then the score. Each item has rank, group_rank, priority_group and no_contact_rule.

### 1.3 Follow-up steps after each write (services/enrichment/followups.py)

The governance service calls these steps after each write to the record: an automatic proposal, an approval and an edit and approve. The steps write proposals only.

1. Window forecaster: each ProjectStageChanged gets a fresh ProcurementWindowForecast (policy automatic).
   - A stage without a window gets a forecast that shows the stage only. For a stage at or after contractor procurement, the forecast has procurement_reached true.
   - The stage change clears the old forecast of the projection, so the calendar never shows the window of an old stage.
   - A forecast that moves six months nearer or more raises the Tier 0 alert t0_forecast_moves_nearer. The threshold and the rule come from config/tiers.yaml.
   - The analysis no longer plans the forecast as a fact. It still calculates the forecast for the scorer features.
2. Opportunities from projects (services/enrichment/opportunities.py):
   - A project that the record gets (EntityIdentified), or that reaches a stage up to contractor procurement, gets one DealIdentified proposal "Diesel supply for <project name>" (fuel_supply_contract).
   - The deal links to the project, its site and its owner, and cites the evidence of the project stage.
   - The proposal is always review, once for each project, and never when the project has an open fuel supply deal or a pending one.
   - The rule is in config/priority.yaml project_opportunity.
3. Demand estimator (services/enrichment/demand.py):
   - A project, or a site, with facts that have evidence for each input of a formula in config/demand-model.yaml gets a DemandEstimated proposal (policy review).
   - The proposal has the label estimate, the formula, the factors and each input with its fact event id and evidence ids.
   - The project takes an input from its own facts first, else from its site. An input without a fact with evidence gives no estimate.
   - demand-model.yaml maps each input to its predicate (fleet_trucks, tonnes_moved_per_year, generation_mw) and its units.

### 1.6 Frontend integration

- services/api/routers/schemas.py gives response models to the approval queue, the decisions, the alert state, the telemetry, the stage move, the engagement results and the priority list. The models keep extra fields at run time. The schema lists the known fields only, so the generated types are exact.
- The client is regenerated (`pnpm api-client`). apps/web/src/api/writes.ts takes each request body and response shape from the generated schema. Only the brief results stay typed by hand (the sources router has no response model).
- The mocked API and the fixture follow the real shapes:
  - Proposals: total, created_by_me, evidence items, and no top-level evidence_ids.
  - Telemetry: items, delivered, delivery_status, time_to_acknowledgement_seconds, false_positive_rate_by_tier_rule.
  - Stage move result: deal_id, stage, stage_pending. The stage move is a human event with a reason and no source evidence.
  - Quarantine: total, reason_codes, the reason text, and the output in the detail only. The reason codes come from config/agent-schemas.yaml.
  - Engagement results, and the decrypted contact fields in data.
  - The priority breakdown: the fixture uses a copy of the calculator, and the mock ranks like the API.
- Modules that changed:
  - The alert telemetry module reads the real metrics.
  - The approval queue sends the EditApprove body.
  - The quarantine module shows the reason text.
  - The relationship panel reads the decrypted contact fields.
  - The timeline shows the reason of a change by the team.
- New provenance controls (docs/07 rule 1): the site name, the status, the operator and the last signal in the site watch list and the site drawer; the stage and each part of the score in the priority list and its breakdown; the stage and the reason in the deal drawer; the deals of a map site; the calendar stages; the demand estimate; the Kanban card.

## 5. Known risks for M7

1. Lead time counts from the last relevant event. It does not age without events. A daily clock event, or a read-time lead time, needs a decision.
2. Criteria 5, 6 and 7 pass against the mocked API only in the browser. The M7 test on the Compose stack must confirm them. The Origination workspace went from 656 ms to 1249 ms, because the priority table now has provenance controls. It is still below 3 s.
3. The end to end test "provenance: a source without licence full shows the quote only" failed once in three full runs under load, and passed on repeat. Check it in CI.
4. Opportunity volume: each approved project gives one pending DealIdentified proposal. A snapshot run adds these to the approval queue. Check the volume with Mohamed.
5. A demand estimate from site facts applies the fleet of the whole site to an expansion project. The label is estimate, but the value can be too high.
6. The forecast shift alert of a reviewed stage is raised at the approval. Its telemetry latency (fetch to alert) includes the review time.
7. uvicorn access logs and the httpx logger in the tests write the SSE access_token query parameter at level INFO. CLAUDE.md rule 5: filter the token from the logs in M7.
8. The lead's Compose database needs migration 0400 and a projection rebuild (`python -m services.projections.cli rebuild`). Without the rebuild, existing deals have no priority values and the new provenance columns are empty.
9. The priority calculator reads the deals of a project for each project event. A rebuild with many deals and events takes longer. It is fast at the current volume.
10. Any change to a router with a response model needs `pnpm api-client`. The CI job "api-client" checks that the generated client is current.
11. The backtest dataset still has 7 events. docs/09 needs 20.
