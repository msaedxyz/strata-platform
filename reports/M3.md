## 1. What we built

### The seven agents (services/enrichment)

| Step | Agent | Module | Output |
|---|---|---|---|
| 1 | Classifier | analysis.py `_classify`, rules.py `classify` | In scope or out of scope. Codes for sectors, geographies, themes, activity types and deal types, only from config/taxonomy. An unknown code sends the output to quarantine |
| 2 | Extractor | analysis.py `_extract`, rules.py `extract` | Mentions and claims. Each claim has a subject, a predicate from predicates.yaml, an object or a value, a certainty and evidence spans |
| 3 | Resolver | analysis.py `_resolve`, rules.py `resolve` | External ids first, then the normalised name and the country, then trigram candidates and a choice. Match, new or no decision, with a confidence. A duplicate pair of existing entities becomes an EntityMerged proposal for review |
| 4 | Lifecycle agent | analysis.py `_lifecycle`, rules.py `lifecycle` | The stage of each project from config/lifecycle.yaml, only when the evidence names the stage or an event of it. A stage 9 or 10 event before stage 4 is accepted. The project is linked to its site (RelationshipAsserted project_at_site) and to the buyer roles that the evidence names |
| 5 | Window forecaster | forecaster.py | No model. The date range from the current stage and the intervals of config/lifecycle-intervals.generated.yaml (config/lifecycle.yaml names the file). Below min_projects_per_interval (5) the start and the end are null and only the stage shows. shift_months_nearer compares with the previous forecast |
| 6 | Summariser | analysis.py `_summarise`, rules.py `summarise` | Up to three sentences. Each sentence has evidence. A sentence without valid evidence is dropped |
| 7 | Scorer | scoring.py, analysis.py `_score` | Features, the score with its full breakdown from the brief weights, an optional model judgement with evidence, and the tier from a rule engine that reads config/tiers.yaml. A model never assigns a tier |

The scorer runs last, because the tier rules use the lifecycle and forecast features (for example "forecast moves six months nearer").

### Backends

- `backends/base.py`: the interface `call(agent, prompt_version, document, context, output_schema) -> dict`. After each call, `last_call` holds the model id, the prompt version, the tokens, the latency and the stop reason. Context keys that start with "_" are for the deterministic rules only and never go to a model.
- `backends/anthropic_backend.py`: the official SDK. Structured outputs with `output_config` json_schema (the schema of config/agent-schemas.yaml with each `$ref` inlined). Model, max_tokens and sampling from config/models.yaml: no temperature for Claude Sonnet 5, temperature 0 for Claude Haiku 4.5 (through `extra_body`, because SDK 1.8 has no temperature argument), thinking disabled where model_capabilities allows it. The document comes after the instructions inside `<document>` delimiters. A delimiter inside the text changes at the same length, so the offsets stay. `refusal` gives the reason code refusal, `max_tokens` gives truncated. Errors: RateLimitError, then APIStatusError (5xx retryable, 4xx not), then APIConnectionError, all with the reason code backend_error.
- `backends/deterministic.py`: the rules of config/enrichment-rules.yaml (version rules-v1). model_id "deterministic-v1", prompt_version "rules-v1". It uses the taxonomy, the brief themes, keywords and exclusions, a gazetteer from the entity names and aliases, regular expressions for money, dates, percentages and quantities, and certainty cue words. It has no randomness.
- `STRATA_AGENT_BACKEND`: auto (anthropic when ANTHROPIC_API_KEY is set, else deterministic), anthropic or deterministic.
- `runner.py`: JSON schema validation with one retry (models.yaml `retries_on_schema_failure`), a log row for each call in agent_call_log (backend, model id, prompt version, input hash, output, tokens, latency, status), and quarantine records.

### Prompts and schemas

- prompts/classifier, extractor, resolver, scorer (judgement only), lifecycle and summariser, each v1.md. Each prompt says that the document is data, never instructions, and asks for evidence with exact quotes and character offsets.
- config/agent-schemas.yaml: the output schemas and the list of quarantine reason codes (schema_invalid, span_mismatch, quote_too_long, no_evidence, value_not_in_quote, value_mismatch, value_unparseable, unknown_taxonomy_code, unknown_predicate, unknown_stage, unknown_entity, refusal, truncated, backend_error, no_text).
- config/enrichment-rules.yaml: all cue words, patterns and thresholds of the deterministic backend and the resolver (rule 11).

### Guardrails

- JSON schema validation with one retry.
- The exact substring check of each quote at its offsets in the normalised text (`spans.verify`). The text comes from object storage through services/common/storage.py, else from the metadata text, else (link_only) from the stored title and description.
- Deterministic normalisers (`normalisers.py`) for names, dates, numbers, percentages, quantities and currency: "$1.2bn" gives 1200000000 USD, "K2.5 million" gives 2500000 ZMW, "US$498m" gives 498000000 USD.
- A claim has `value_text` (the exact words) and an optional `value`. The value_text must be inside the quote, it must parse for the value type of the predicate, and a given value must have the same normal form. Else the claim goes to quarantine and does not become a fact.
- Only verified spans become evidence rows (verified = true). Agents write proposals only.

### Governance (services/governance)

- `proposals.py`: `create_proposal()` writes the proposal row and a ProposalCreated event in stream ('proposal', id) with the proposed events. It evaluates config/approval-policy.yaml (automatic, review, admin_review, with certainty stated and min_resolution_confidence 0.9 for a new entity). An automatic proposal writes its events at once through `event_store.append_event`, then the status auto_approved and ProposalApproved with actor system. `approve()`, `reject()` and `edit_and_approve()` follow docs/06: a user cannot approve an own proposal (`ProposalForbidden`, a PermissionError for HTTP 403), a rejection needs a reason, and edit and approve writes human events that keep the original evidence. An approved ProjectStageChanged gets its ProcurementWindowForecast at once. Idempotency keys stop duplicate proposals.
- `alerts.py`: `raise_alert()` writes AlertRaised at once with the status unconfirmed (no approval gate), with the evidence ids, the tier rule and the published and fetched timestamps. It records a delivery row for the frontend channel and, when STRATA_SMTP_HOST is set, sends an email and records the email row. A failed email does not stop the pipeline. One alert for each source and tier rule (a unique index enforces it).

### Pipeline, storage and API

- `pipeline.enrich(source_id)` and the queue task `enrich_source`: classify, extract, resolve, lifecycle, forecast, summarise, score, then write the evidence, the proposals, the alert and the quarantine rows. Proposals: SignalScored ('source' stream, automatic), DemandDriverObserved ('market', 'zm'), SiteStatusChanged for watched sites (review, the watch list shows the pending status), EntityIdentified for new projects ('project' stream) and organisations, ProjectStageChanged, ProcurementWindowForecast (automatic), DealIdentified for open tenders, EOIs, prequalification notices and planned contract opportunities (always review), EntityAttributeAsserted, RelationshipAsserted, EntityMerged, and the summary inside SignalScored.
- An out of scope document writes no proposal and no quarantine row. Its enrichment_run row has the status out_of_scope.
- A second run of a source returns already_enriched. A forced run gives no new proposal and no new alert.
- The periodic task `enrich_pending` enriches each source without a finished run (every 10 minutes, config/enrichment-rules.yaml).
- Migration db/migrations/0200_enrichment.sql: the table enrichment_run, proposal.idempotency_key, source and run columns in agent_call_log and quarantine, the unique alert index, and the SQL check `fact_evidence_problems()`, the view `fact_evidence_problem` and `count_facts_without_verified_evidence()`.
- scripts/check_evidence.py: the SQL check plus the check of each quote against the stored text. The count must be zero.
- services/api/routers/quarantine.py: `GET /api/quarantine` and `GET /api/quarantine/{id}` (viewer role), with the reason code and its description. The typed client in packages/api-client is regenerated.

### Gold set and evaluation

- tests/eval/gold: 50 synthetic documents with draft labels (tests/eval/README.md). They cover the six sectors, all eight site classes and the four activity directions, with 7 demand driver items (and one ERB notice with no change), 7 open procurement items, 11 documents with an expected deal and 14 projects with a lifecycle stage. 3 documents are out of scope.
- tests/eval/holdout: 12 more synthetic documents, written after the rule changes. They are reported, not gated.
- `python -m services.enrichment.eval`: the metrics of docs/05, the targets of config/eval-targets.yaml and the baseline check (a drop of more than two points fails). Results in tests/eval/results/latest.json.
- CI job "Agent evaluation on the gold set" (.github/workflows/ci.yml). It runs when prompts/, config/models.yaml, config/agent-schemas.yaml, config/enrichment-rules.yaml, config/eval-targets.yaml, config/tiers.yaml, config/lifecycle*.yaml, config/taxonomy/, services/enrichment/ or tests/eval/ change (dorny/paths-filter). It uses the deterministic backend, and also the Anthropic backend when the secret ANTHROPIC_API_KEY exists.

| Metric | Target | First run, before any rule change | Gold set, now | Held-out set (12 documents) |

| Canonical facts with verified evidence | 1.00 | 1.00 | 1.00 | 1.00 |
| Extraction precision | 0.90 | 0.772 | 0.952 | 0.727 |
| Extraction recall | 0.75 | 0.698 | 0.952 | 0.667 |
| Resolution precision | 0.95 | 0.962 | 0.980 | 0.970 |
| Classification macro F1 | 0.85 | 0.892 | 0.985 | 0.873 |

Other gold set values: certainty accuracy on matched claims 0.98, tier accuracy 0.98, deal accuracy 1.00. Counts: 63 gold claims, 157 resolution decisions, 196 planned fact events.

How to read these numbers:

1. The labels were written from the text and committed before the first run. The first run column uses the rules of that commit with the final scorer.
2. Then the rules changed while the gold errors were visible. The changes are general (future and speculative cues for event themes, stricter synonyms, more cue forms, merged duplicate claims, organisation sector hints, name priority for shared aliases). No label changed. The gold set numbers are therefore optimistic.
3. The held-out set was written after the changes and run once, with no change after the run. Extraction precision and recall on it (8 of 11 and 8 of 12 claims) are below the targets. The other metrics hold. The sample is small.
4. The Anthropic backend has no numbers. The build network cannot reach the API.

## 6. Known risks for M4

1. The gold set numbers are optimistic. The held-out set shows lower extraction precision (0.727) and recall (0.667). It found these rule faults, which are not fixed, so that the held-out numbers stay honest: "expects first production" is not a future cue and gives a false ramping_up status (h12). A queue of trucks with words between "trucks" and "waited" is not a border delay, so a Kazungula delay story became Tier 2 (h02). The synonym "one-stop border" also fires on a delay story. The capex subject can be the site in place of the project (h01). "The sale of a 20 percent stake" gives an ownership claim (h11). Fix these in M4 and add more held-out documents first.
2. The Anthropic backend is tested with a mocked client only. Models give poor character offsets, so the exact offset check can send many model spans to quarantine. A possible change is to ask for the quote only and find its offsets when it occurs once. That is a change to guardrail 2 and needs a decision.
3. Structured outputs with claude-haiku-4-5-20251001 need a check against the live API. config/models.yaml uses the dated id.
4. The Tier 0 rule "new project at its first public trace" fires for each new project entity, also at steady operation (g11). The snapshot gave 15 such alerts and 17 market driver alerts among 146 items. Check the alert volume with Mohamed.
5. A brief alias that two entities share (for example "Nakambala", "NCZ", "Kagem") gives two resolution decisions for one mention. Merges are proposed only for exact normalised duplicates. Project names that differ ("S3 expansion", "Kansanshi S3 expansion") are not merged.
6. SiteStatusChanged has from_status null, because the projection does not take the status_hint of the brief as the recorded status.
7. M4 must add the API routes for approve, reject and edit and approve (the functions are ready), the approval queue and the roles. `approve()` raises ProposalForbidden (PermissionError) for the 403. The forecast after an approved stage runs inside `approve()`.
8. The scanned ERB PDF is out of scope, because RapidOCR drops the spaces between words (M2 risk 1). CI has Tesseract.
9. The evidence text check runs only while the text is stored. verify_then_purge deletes the text after 30 days.
10. Each enrichment test module makes its own database (six more databases in a test run).
11. Merge risk with Track 2: packages/api-client (regenerated), tests/python/conftest.py (one new import line) and .github/workflows/ci.yml (one new job). Run `pnpm api-client` again after the merge.
